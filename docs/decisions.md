# Проектные решения

## Архитектура

### Фронтенд

Фронтенд системы разделяется на служебный (для библиотечного персонала) и пользовательский (для читателей).
Служебный фронтенд решено делать в виде SSR сайта на основе шаблонов Thymeleaf и Spring MVC.
Пользовательский фронтенд решено делать в виде SPA приложения на основе React.
Это разделение сборки и поддержки интерфейсов обусловлено как спецификой эксплуатации (библиотечный интерфейс неразрывно связан с системой, а пользовательский опционален), так и клиентоориентированностью по части эргономики.
К тому же факт создания отдельного веб-приложения для пользовательского фронтенда закладывает возможность создания и мобильного приложения при необходимости.

### Бэкенд

В качестве архитектуры бэкенда выбран модульный монолит.
С одной стороны, это позволяет сразу разделять код на домены (подсистемы), делая его чистым и пригодным для возможного перехода на микросервисы.
С другой стороны, сознательно отвергается изначальная разработка микросервисной архитектуры ввиду отсутствия команды и неоправданных накладных расходов на инфраструктуру.

Модули организуются на основе POM конфигураций. Так, есть общий `backend` модуль с типом сборки `pom` и шесть модулей с типом сборки `jar` внутри него.
Модули `common`, `auth`, `catalogue`, `lending` и `profile` представляют собой библиотечные модули без рантайма (в рамках модульного монолита).
Модуль же `entrypoint` зависит от всех остальных и является единой точкой сборки приложения, создавая `SpringBootApplication`.
Таким образом, идея модульного монолита воплощается в том, что разработка ведется по непересекающимся доменам, а артефакт сборки один.

Бэкенд-модули будут предоставлять как контроллеры для функционирования SSR библиотечной панели, так и контроллеры RESTful API.

### База данных

Исходя из модульности бэкенда, реляционная база данных разделяется на физически независимые схемы в соответствии с доменами модулей.
Это схемы `auth`, `catalogue`, `lending` и `profile`.

## Реализация

### Миграции БД

В связи с тем, что инструмент управления миграциями Flyway по умолчанию не рассчитан на использование в модульных проектах (когда домены разные, а артефакт сборки один), было принято решение о "версионном" именовании миграций в форме "Vn.m_...", где n - кодовый номер модуля, а m - порядковый номер миграции в нем.
